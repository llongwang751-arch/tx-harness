## 这次具体推进了什么

WorkBuddy 的第一轮固定响应校准 WBC00 已实际提交。它先发了一个不带工具的请求，原先只允许“工具调用→工具回包”的服务拒绝了请求。第二轮 WBC01 把这种请求单独固定回复并计数，随后看到了 23 个内置工具声明，其中有 ToolSearch，却没有 probe_commit。两轮都保留为适配未知，不能判成产品工具调用失败，也不用于通过率排名。

25日补归档的[第三轮WBC02](controlled-workbuddy.md)已登记固定ToolSearch桥接方案，但固定参数在适配器schema校验阶段被拒绝；ToolSearch实际派发0、共享probe调用0。服务超时结束，最终窗口最小化，原生终态未知。三次都是独立校准任务并计未知，元宝、豆包仍为零新任务。

后续仅在取得足够实际schema约束及支持依据时，才另登记一次最小校准，检查它是否公开contract工具及相同schema。只有实际共享 MCP 收到原参数、产物或错误回包对应，且桌面任务正常结束，才算接通。这个发现步骤是 WorkBuddy 的额外条件，后续比较须保留它，不能说五款调用过程完全一样。

## 停止与重开条件

元宝本轮在模型、设置、工具及技能菜单检查后停止；豆包云电脑在模型菜单、工作模式设置及明确的本地连接器限制处停止。重复发送业务题无法证明共同模型可控，所以不为此追加任务，也不填零分或满分。只有取得本入口可用的正式接口、版本或权限变化，才重开固定模型实验。

如果后续改测豆包本地 STDIO，必须独立登记为本地模式，并保留真实模型对选工具、改参数的影响；它可以补充工具边界证据，不能补成云电脑已完成同模型对照。

Skill 的问题也分开处理。元宝的账号授权、豆包的技能选择，都不证明内置或隐藏 Skill 全部关闭。WorkBuddy 的固定程序不解释 Skill 文字，但已有个人插件和系统上下文仍保留。当前方法控制的是指定动作的生成与传递；默认模型的业务表现、完整 Skill 消融和原生权限沙箱，仍需要不同证据。

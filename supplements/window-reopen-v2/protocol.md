# 窗口重开v2：直接取回原件与模型续接分开验收

登记日期：2026-10-22。v1两次真实提交及其未知判断原样保留。本批最多两个全新任务，依次R01-reopen、R02-control；本协议、输入和代码在首次提交前冻结推送。预检没有发送新的模型任务，不算新增独立运行。

## 研究问题与归因对象

主问题：第一阶段结束、正确原件已存在时，窗口重开后是否仍能通过同一任务的原生界面访问原消息，并分别将最初附件和stage-a.txt另存为完全相同的字节？这些步骤只操作客户端界面，不向模型发送恢复、复述、重新生成或修复请求。先固定要保存的消息、文件和正确字节，再检查Harness的可见恢复与交付边界，避免用模型答题能力作为主指标。

主指标是客户端可见恢复及本地文件交付，不是远端存储耐久性。原附件在主机上的源文件保持存在；原生另存的副本能证明该界面取得的字节，不能证明字节来自独立云端存储或后台实际加载给模型的上下文。模型、隐藏Skill、后台路由和全局记忆仍不能独立固定，因此第二阶段复制和receipt生成只列联合结果，不单归Harness，不给五产品纯Harness排名。

## 预检及固定条件

本批前已在v1封存任务上完成无模型提交的入口预检：原附件卡可直接打开，更多操作有“另存为”，经原生另存获得的128字节副本SHA等于原输入；发正常关窗命令后两次独立窗口清单均为空，之后才启动客户端。此次不覆盖v1缺失的历史观察。

固定WorkBuddy Windows V5.8.3、办公入口、Deepseek-V4.1-Flash标签和允许完全访问，不主动安装/调用Skill或更新软件。实际可见条件每臂再次采集；变化则记录偏离，停止配对推论。每臂只有一个全新任务，一次仅一个执行者。新工作空间和附件副本都在仓库外，不能给产品评测代码或答案。

使用同一份[probe.txt](fixtures/probe.txt)和[prompt.txt](fixtures/prompt.txt)，二者SHA在protocol.json固定。R01/R02工作空间位于D:/harness-window-reopen-v2下，提交前各自为空。绝对路径和执行时间不同，顺序固定，保留为限制。重复次数不用于估计总体可靠性。

## 冻结流程

1. 全新任务、选定独立工作空间、附加probe.txt、粘贴冻结提示词。记录发送动作前后墙钟与单调时间、配置及初始界面。一次初始发送算一次产品运行；后续操作和两个阶段不另计次数。
2. Stage A正常结束后，确认原生stage-a.txt卡片、消息和任务身份。由原附件卡打开probe.txt，通过其原生“另存为”取得`retrieval-before/probe.txt`；同样从stage-a.txt卡片取得`retrieval-before/stage-a.txt`。只写预建的观察者收集目录，不覆盖原输入或原件。复制完成必须等界面就绪并核对文件名，再保存，不能在对话框尚未出现时盲发快捷键。
3. 两份实际取回副本均与冻结输入SHA一致，且消息和任务已采集，才设检查点T。Stage A失败或取回失败也保留真实提交和原因，不补提示修复，不删除分母。
4. R01发一次正常主窗口关闭命令。之后只观察、最多30秒/8次窗口清单，要求连续两份清单均无该WorkBuddy应用窗口；最后一份为空的观察完成之前严禁调用启动接口。保存非空和空清单、时间及顺序。无法证实就记录未知，不启动后追补。成功后才用官方原生启动接口重开，凭新空间、唯一研究标记、原消息、任务标题和创建时间回到原任务。R02保持原窗口，执行相同的文件取回和消息观察。
5. 两臂在T后、续接之前，重新从最初消息附件卡打开probe.txt并原生另存`retrieval-after/probe.txt`，从既有交付卡打开stage-a.txt并另存`retrieval-after/stage-a.txt`。不把已经另存的观察者副本当成原附件重新取回。不发送任何模型消息来找文件。记录实际另存来源及目标、各次取得的字节和时间。
6. T后180秒（允许±15秒）发送唯一消息“按初始要求继续第二阶段。”。180秒包含关窗、观察和取回，不因失败调整时间。第一阶段和直接取回均成立后才进入该步；缺失或超时按原因记未知/失败，不追加任务替换。
7. Stage B结束，取得stage-b.txt及receipt.json，按复用的冻结文件契约判卷。receipt只能有stage/source/bytes/sha256，值为B、probe.txt、输入整数字节数和SHA-256小写十六进制；重复键拒绝。记录本地原件来源，结束后封存并正常关窗。

## 验收与计数

| 指标 | 通过条件 | 置信范围 |
|---|---|---|
| 原消息可访问 | 同一任务的完整初始消息可通过原生UI访问，且研究标记、标题、创建时间对应 | Operator采集，中置信；不推断后台上下文 |
| 原附件直接取回 | 前后均从原消息卡原生另存，取得字节与固定输入一致，来源/目标操作可追溯 | 字节高置信；界面来源中置信，不证明云存储 |
| 既有交付直接取回 | 前后均从原生stage-a.txt交付卡另存，字节一致 | 同上；本地文件一直存在是明确条件 |
| 关窗干预成立 | 关闭后两次连续空清单，启动发生在两次观察之后；同一研究任务恢复 | 记录顺序可复算，现场仍依赖Operator |
| 模型续接联合交付 | Stage B文本相等、receipt契约通过、实际原件预算内取得 | 字节高置信；模型、Skill、Harness共同作用 |

主观察的有效性要求固定输入、可见配置、同一任务、规定动作和直接原生取回来源均可确定。缺证列未知，已知产品失败列失败；有效包括已知通过和已知失败。若界面操作/采集错误导致条件未知，不能记产品失败。主观察与第二阶段的联合文件结果分别给出，不能用一个通过补另一个缺口。

## 预算、证据及停止条件

每臂从初始发送动作前起最多1200秒，含等时等待与重开。口径为“评测侧预算内已实际取得并封存的字节”，不声称有远端第1200秒全量状态。每次副本创建前确认目标不存在；通过UI保存后记录时间、大小和SHA，再复制进私有证据目录。任一份不稳定或晚取得的字节单列，不能反推早期成功。

提前完成则提前封存：清单必须覆盖前后各两份UI取回副本及最终stage-a/stage-b/receipt三份原件；每次收集唯一对应日志、原始副本和SHA。公开副本不得覆盖。原生截图只发布经检查且无其他任务/账户的原图；AX仅发布逐行审阅的任务摘录，保留源SHA和行号。

本批至多两任务，不按结果增加次数。主条件或时间不成立时保留现场与偏离；下一问题另登记，不更改本协议。原有模型/Skill独立归因、旧截止快照、v1关窗历史缺口仍保留，不能用本批覆盖。最终交付报告须把现象、原因线索、验证结论和仍未知的变量分开写。

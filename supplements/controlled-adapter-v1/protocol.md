# 固定动作下的 Harness 工具契约对照

作者：李明远。登记于2026-10-24，正式运行前提交并推送。两产品入口已分别校准；旧失败、补丁修订和代码版本保留在各 calibration*.json，不混入正式四臂。

## 任务、输入、完成条件

两款真实产品使用同一个本地固定响应服务、同一个 stdio MCP 源码、同一个工具输入对象，输入见 fixture.json，任务文字见 prompt.txt。服务第一次只给出 probe_commit 调用，第二次只在对应 call_id 的真实工具结果出现后结束。它不解释提示词、Skill 或任务要求，不调用神经模型。正式顺序冻结为 DSH错误、Codex成功、DSH成功、Codex错误；一次只执行一个，退出该实例后继续。

每臂新任务、空工作区、新配置目录；120秒上限，只初始提交一次，不自动重试、不补跑替换。MCP成功臂实际写入artifact.txt；错误臂实际返回isError=true和E_FIXTURE_DENIED，不应产生文件。除此以外，两种工具行为的代码、参数、schema相同。产品身份、协议编码和包装不同，均单独记录。

## 观察与赋分

以下四项分别记通过1、不符合0、证据不足null，不加权合成产品排名。只有所有项可判且通过时，本次契约记pass。错误臂不要求模型自行恢复，也不把预期错误计为产品失败。

1. C1调度：固定服务发出动作后，真实MCP日志恰好一次tools/call，工具名和参数对象与冻结输入完全相同；缺少真实执行不能用native请求界面替代。
2. C2效果：成功臂原件125字节且SHA与输入UTF-8字节相同；错误臂回包为固定错误对象且没有artifact.txt。未知缺文件不能自动判错误处理通过。
3. C3回传：第二次模型请求包含相同调用ID和真实MCP返回中的固定对象，无字段丢失或修改。协议包装可不同；记录原包装。isError是否另有结构化保留单列，不用结束文本证明。
4. C4终止：恰好两次本地模型请求，第二次给出固定CONTROLLED_DONE，官方普通事件可见正常终止且进程退出码0，实际收集在预算内。

主要判断绑定协议版本、输入、实际启动配置、模型端点请求、MCP服务端请求/返回、普通产品事件、文件和理由。hash提供字节对应，不独立证明操作员采集真实性。外部人工复核尚未完成。

## 模型、Skill与Harness归因

- 模型：本轮不用真实语言模型，用固定程序逐次发出同一canonical动作。它不评价答案，也不从产品表现生成新动作。真实产品接收固定动作后，是否调用工具、如何传参和回传，属于本轮观察对象；固定服务自身不是被测Harness。
- Skill：DSH通过本次补丁关闭filesystem/Office Skill提供器、tool-skill和agent-instructions。Codex隔离用户配置、跳过宿主发现、关闭扩展、显式禁用四个已知系统Skill路径；校准仍观察到Skill目录标题，故不宣称完全删除。固定程序不执行Skill指令，所有实际工具调用与固定动作核对，不把Skill文本影响生成动作混入这条路径。
- 仍未控制：产品各自系统上下文、内置工具目录、wire codec与schema包装、实现版本。它们属于记录条件；共同MCP客户端以外的Harness功能未测，不能从本轮外推一般能力或纯数字因果效应。两种wire codec有离线正例和近似错误反例测试。
- 可信MCP进程在宿主执行文件写入，绕开产品原生文件沙箱；本轮不评价权限边界，不替代已有S02。
- WorkBuddy、元宝专家、豆包工作任务没有在本轮验证共同provider入口，仍留在原真实任务轨道。没有证据就不改写为五产品都实现同模型/完整Skill控制。

## 停止与复核

冻结四臂执行完即停止；失败或未知也必须公开并留在分母。出现不兼容协议先保留现场，判适配器/校准未知，若需改代码另立协议。后续只在真实新入口能改变具体归因问题时扩展，不继续扩大相同题目数量。

从公开包复算只读验证，不会启动产品或调用模型。复现真实任务则需要Windows、登记版本的官方CLI/SDK及Python，使用新run_id与新登记，不覆盖既有包。原账户、用户配置、隐藏推理和Skill正文不在公开证据范围。

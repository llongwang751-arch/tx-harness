# 原75轮确认性方案草案（未实施）

本次实际交付先读[已执行的评测方案](evaluation-plan.md)。本页用于追溯早期设计，不是当前实验完成清单。

本页保留2026-10-13的确认性方案草案，75次主实验未实施。2026-10-16的当前执行口径见[方法修订](revision-v2.md)、[原25现场派生复核](../reports/evaluation-v2.md)和[另行预先登记的固定文件契约补测](../supplements/contracts-v2/protocol.json)。这些修订不追认旧预试为正式实验，也不改写冻结config/cases或旧分数。

本方案比较 Codex、WorkBuddy、DSH（用户确认指 DeepSeek Harness）、元宝专家模式和豆包办公。名称只是待登记的产品标识；入口、发布者、版本和可用模式必须在开跑前核实。尤其不能仅凭“DeepSeek Harness”这一名称，把任何 DeepSeek 聊天入口视为同一产品。

评测分为两个层次：主实验衡量用户通过各产品完成任务的端到端表现；归因补充在可匹配的模型、指令和运行条件下检查 Harness 行为。主实验的分数包含模型、内置 Skill、工具与运行环境的共同影响，不能直接解释为纯 Harness 因果排名。责任判断遵循 [归因规则](attribution.md)。

## 1. 研究问题和观察单位

需要回答的问题：

1. 面对相同任务与输入，五款产品能否交付满足完成条件的产物？
2. 它们在规划、工具执行、状态保持、故障恢复、结果验证和可复核性上有哪些可见差异？
3. 哪些差异有匹配条件下的证据支持为 Harness 行为差异，哪些只能归为产品整体差异？

一次运行是“一个产品，在一个新会话中，对一个任务的一次独立尝试”。主实验计划包含 5 个任务 × 5 个产品 × 3 次重复，共 75 个预定槽位。重复执行不是增加独立任务数量；所有结论都须注明本评测只有 5 类任务、每个产品每任务只有 3 次重复。

如果某产品经预检发现可能没有满足任务要求的入口，仍保留对应槽位；在正式操作验证并保存现场后才能记录“不支持”，不伪造执行过程。报告同时披露计划槽位数、实际启动数和可评分数。

## 2. 开跑前登记并冻结

在首个计分运行开始前，提交 Git 提交并登记以下项目。之后的变化要有时间、理由与影响说明，不得看到表现后改变权重或成功标准。

先开展不进入主统计的预试（`pilot`），检查各入口能否接收材料、交付文件，以及验收规则是否无歧义。预试结果不能复用成主实验重复。任务、入口与细则确定后，将配置中的协议状态从草案改为 `preregistered`，提交冻结，再生成正式顺序和运行包。冻结后不能在原批次中修改输入、评分代码、方案或细则；修改须另建实验批次，保留原版与变更说明。

| 项目 | 必填内容 |
| --- | --- |
| 产品身份 | 官方入口、发布者、产品版本或构建号、桌面/网页/API、模式、账户层级、所在地区 |
| 模型条件 | 可见模型名称与版本、能否选择、是否自动路由；不可见时填写“未知”，不能自行推断 |
| Skill 条件 | 用户可选 Skill、版本、是否启用、可否关闭；不可见内置 Skill 填写“未知” |
| 环境 | 操作系统、浏览器、网络、时区、语言、输入方式、工具权限、可访问的文件与服务 |
| 任务材料 | 任务 ID、原始提示词、输入文件校验值、完成条件、允许的外部资料、独立验收办法 |
| 预算 | 各任务统一的墙钟上限、统一人工补充次数与操作规则；可控时固定模型调用/费用上限 |
| 评分 | 5 维 100 分细则的版本、任务权重、维度权重、缺失值与失败处理、聚合公式 |
| 调度 | 随机种子、每轮顺序、重复编号、测试窗口与产品更新的处理规则 |
| 证据 | 录制方式、可导出日志范围、证据目录、脱敏规则、复核者与复核步骤 |

预算原则是统一可观察的用户投入，不宣称统一不可见的计算量。主实验每次运行 20 分钟，最多 2 次非预定人工干预。T04 按用例规定补发输入属于预定动作，不占干预次数，但补发和等待都占 20 分钟预算。某些入口无法控制 token、内部模型调用或自动重试时，只记录可见值，把这一限制列为混杂因素。不得用估计值代替真实计费或调用数据。

主实验配置以 [config/protocol.json](../config/protocol.json) 为准。评分由 [统一评分细则](rubric.md) 与 [config/rubric.json](../config/rubric.json) 定义：客观结果 60 分，文件交付与工具落地 15 分，执行反馈与恢复 10 分，约束与权限边界 10 分，用户操作负担 5 分。四个人工维度均使用 0–4 整数等级，按“维度权重 × 等级 / 4”换算。每个任务自动检查项的权重和为 100，再按通过权重比例换算成客观结果的 60 分。执行者不能临场添加评分项。预注册要指向细则的具体版本或提交号。

## 3. 任务与完成条件

五个任务应覆盖不同任务链，而不是同一能力的五种措辞。用例文件必须分别包含：

- 任务 ID 与研究目的；
- 所有产品逐字一致的初始用户提示词；
- 输入文件、依赖条件及其校验值；
- 可访问的目录、服务、网络范围和输出格式；
- 可通过独立工具或人工复核检查的完成条件；
- 统一的预算、人工回复规则和失败注入位置；
- 哪些结果属于可接受替代交付，哪些只算部分完成。

完成条件须描述结果。例如要求“提供可打开的文件，所有指定字段正确，引用可定位到给定资料”，不能用“模型表示已完成”作为通过条件。要求下载产物时，只有聊天文字而没有可取回文件不能视为完整交付；允许文本交付的任务则不能因为缺少下载按钮扣分。

任务应使用合成或获授权材料。原始数据有意包含的缺项、重复、错误或冲突须在验收答案中登记，不能事后把模型碰巧发现的问题写成预设考点。验收答案不提供给被测产品。

## 4. 对照条件

### 4.1 主实验：固定任务，比较产品整体

所有产品使用同一份任务提示词和同一版输入。统一语言、输出要求、完成条件、人工预算和网络政策。默认不联网获取任务内容；联网登录产品不等于允许自行补充外部材料。每次开始新的会话，并关闭可控的记忆、自定义指令和无关插件；无法关闭的项目列为已知差异。主实验不安装用户 Skill，内置 Skill 不能查看或关闭时记为 `unknown`。

使用产品默认配置，在开跑前登记并锁定每个产品的默认模型选择与模式；不能在每次运行中改选有利模型，也不能在看到失败后换模式、换模型或临时补装 Skill。界面自动路由且无法锁定实际模型时，如实记录，不能声称底层模型保持一致。模型与内置 Skill 不同是主实验的条件差异，必须展示，不能用“同一提示词”声称这些变量已被控制。

产品需要不同文件上传或工作区导入方式时，使用内容一致的原始文件，并记录适配步骤。若必须转换格式，保留转换脚本或步骤及转换后的校验值，检查内容是否损失。输入已经改变的运行不得冒充严格匹配运行。

每次通过仓库的准备工具生成独立 `run/workspace`，产品只能接收其中的 `inputs`、提示词和空的 `outputs` 交付区。不得开放评测仓库、验收答案、检查器或此前运行产物。Codex 等能够读取本地文件的入口尤其需要限定工作区；把评测者仓库直接作为被测工作目录，会泄露答案并使运行无效。

工作区分离不等于操作系统级隔离。需要记录入口实际可以读取的目录和是否有权限边界；无法限制或核实范围时，披露答案泄漏风险。公开用例及答案也可能产生预读或模型记忆污染，报告注明公开时间、运行时间与操作者是否看过答案，不把公开任务称为防污染盲测。

### 4.2 通用指令卡与原生 Skill 实验分开

默认主实验使用统一任务指令，不为某一个产品定制提示词。若研究通用工作流程，另设补充实验：所有产品收到同一段可读的通用指令卡，明确规划、操作、验证与交付步骤。把指令卡通过聊天输入不等于装载了同一原生 Skill。

原生 Skill 补充实验单独登记产品、Skill 来源与版本、实际启用证据、模型和任务。产品不能装载同一 Skill 时，不计入“同 Skill”对照；相似名称不代表相同实现。原生 Skill、通用指令卡和默认模式结果分别呈现，不混成一个总分。

### 4.3 条件匹配的 Harness 归因补充

在确实可以配置的入口上，尽量匹配同一模型版本、采样设置、上下文预算、指令卡、工具契约、输入、权限、运行环境与输出限制。记录哪些条件严格匹配、哪些仅近似、哪些未知。

每次只改变一个拟研究的因素，例如自动重试策略或任务状态保存方式；变更前后的任务与验收保持一致。单纯把五款产品换成同一家模型，并不足以控制隐藏的系统指令、模型路由和工具协议。

只有对照满足 [归因规则](attribution.md) 的证据要求时，才能作局部 Harness 归因。无法达到条件时，把结果保留为行为诊断或产品差异，明确“无法完成纯 Harness 因果隔离”。不为了凑齐排名降低条件要求。

## 5. 调度与逐次运行

通过 `plan` 生成调度：5 任务 × 3 重复构成 15 个“任务—重复”区组，按预注册种子打乱区组顺序，再在每个区组内独立打乱 5 个产品顺序，共 75 个槽位。重复编号不要求按数字顺序执行。尽量让同一组的五产品运行处于接近的时间窗口，降低版本更新、网络与实时资料变化的影响。保留生成的顺序表与配置指纹，不根据结果调换次序。

每次运行依次执行：

1. 检查任务材料、产品模式和权限是否与登记表一致。初始化干净工作目录和新会话，开始记录。
2. 导入同一版输入。记录导入失败、文件大小限制、格式转换和用户花费的准备时间。
3. 提交冻结提示词，并记录提交成功的时间。墙钟计时从提交成功开始，包含执行中的等待、重试与人工回复；输入准备时间另报。
4. 对产品提出的澄清，使用预先写好的答案。除了 T04 预定补发等用例明确规定的动作，其余回复占用一次非预定人工干预预算。如果没有对应答案，只能回复固定的“请按任务中的已知信息继续，缺失信息请注明”。
5. 对权限确认，只作预注册允许范围内的确认，记录次数与时间。权限点击、文件选择与登录等操作必须记录，但不与内容性回复混计。
6. 只有任务事先允许的情况下才能给进度提醒；使用冻结措辞并占用非预定人工干预预算。不能向某产品指出答案错误、代写代码或手动修好产物。T04 如 2 分钟内没有主动询问，可按预定规则释放补充输入，事件中标明“预定释放、非自主发现”，不把它评分为产品主动找回缺失信息。
7. 产品宣告完成、明确放弃或达到时间上限后停止。保存当前产物、用户可见过程和停止原因；不能让超时运行继续改善计分结果。
8. 在评测环境中独立打开、运行或检查交付物。保存检查命令、结果和可定位的证据，按统一细则评分。

工具对应关系：`prepare` 创建无答案工作区；实际条件填写在 `meta.json` 中的 `operator`、`surface`、`product_version`、`model`、`model_visibility`、`skill_condition` 等字段，未知项用明确的 `unknown` 描述，不留空。`event` 登记实际发生的开始、操作、错误、人工干预和结束，证据文件位于该次运行的 `evidence`。T04 用 `release` 登记预定补发，再另外保存真实界面上传与用户消息现场；复制文件回执不能代替上传证据。`finalize` 记终态，填写 `manual.json` 后执行 `seal`，由 `score` 与 `report` 计算结果。所有现场时间必须包含时区，人工回填使用实际发生时间，不能以登记时间冒充执行时间。

不把“正在思考”之类 UI 动画当成工具调用证据。需要过程记录时，只使用用户可见的操作、工具事件、会话消息、屏幕录制或官方导出。不得要求或尝试提取隐藏思维链、私有系统提示词或未授权内部日志。

产品更新或账号条件改变发生在一个测试批次中途时，先停止该批次，登记差异。可以重开完整批次或按版本分别报告；不能把变化前后的结果无说明地合并。

## 6. 故障注入与恢复

故障必须发生在实际输入或评测服务中，并且所有参加该项对照的产品接收相同条件。不能只在提示词里谎称工具失败，再把回答当作真实恢复证据。主任务中预设的故障计入主实验；临时加入的诊断故障只进入补充实验。

| 注入 | 可操作设置 | 可观察结果 | 限制 |
| --- | --- | --- | --- |
| 缺失文件 | 输入说明引用一个预先登记但实际不存在的可选文件，必要信息仍在其余输入中 | 是否定位缺项、避免编造文件内容、采用允许的备用输入、说明影响 | 必需文件缺失而无法完成时，正确求助可获得恢复观察项的相应分，但不视为完成原任务 |
| 临时服务错误 | 如各入口均可调用同一测试服务，使同一个请求前 2 次返回 503，第 3 次恢复；保存服务日志 | 是否有有限重试、等待或备用方案，是否重复产生副作用 | 不能接入同一服务的入口不纳入该匹配归因实验 |
| 格式损坏 | 提供同一个可解析的大部分内容和一个预先登记的损坏字段/工作表 | 是否识别问题、保留有效内容、报告修复或缺失范围 | 输入转换造成的额外损坏属于评测适配问题，应单独处理 |
| 写入受限 | 在支持真实工作区的入口，将预定目标目录设为只读，另提供可写的备用目录 | 是否准确说明失败、改用允许路径并成功交付 | 纯聊天入口没有对应文件系统时，标记该诊断不适用 |
| 会话中断 | 仅在支持恢复的入口，于预定操作边界关闭并重新打开同一会话，不给新的解题信息 | 是否保存任务目标、产物和待办状态，是否安全继续 | 未提供恢复入口是可见产品限制；不能据此断言内部状态丢失 |

至少选一项所有主实验入口能够接收的输入型故障。工具级与状态级故障可以作为单独的能力诊断，不强行转换成看似通用但条件不同的任务。

## 7. 运行状态、计分和有效分母

先判定记录状态，再按评分细则判定表现。记录使用以下英文状态码；“部分完成”和“记录缺失”是额外的表现/证据描述，不能代替状态码：

| 状态 | 判定标准 | 主实验处理 |
| --- | --- | --- |
| `pending` 待采集 | 尚未实际启动、只有模板或计划 | 不评分，不纳入主统计；绝不当作失败 |
| `completed` 完成 | 已启动并结束执行；最终是否满足条件仍由独立验收判定 | 按证据赋分，不自动满分 |
| `failed` 任务失败 | 已启动，但产品明确失败、放弃或没有完成规定交付 | 按实际可验收部分赋分；保留可能存在的部分产物 |
| `timeout` 超时 | 已启动，达到统一时间上限 | 使用截止时产物评分，单列超时率，不删除记录 |
| `unsupported` 平台不支持 | 在正式入口操作后，证实无法接收规定输入或进行必需操作，且没有有效交付；保存现场 | 保留槽位，端到端完成率记失败；客观结果 0 分，其他维度按真实现场评分；不进入条件匹配归因分母 |
| `infra_error` 评测基础设施故障 | 评测者错输入、错模式、计时或录制系统故障、评测服务配置错误等破坏实验条件 | 保留审计记录并排除主统计；按预注册规则重跑同一槽位 |

不能凭营销页面、主观印象或找不到入口就预先给产品填 `unsupported`；必须保存正式操作验证证据。已有可验收的部分产物时，按 `completed` 或 `failed` 的实际状态记录部分表现，不能标成 `unsupported`。产品运行期间自身的报错、服务失败或权限拒绝不能为消除低分而改成 `infra_error`。一次无效重跑不增加独立重复数，原始记录和重跑关联须保留。

任务失败、超时可以与记录缺失同时出现，分别记录主停止状态和证据完整性。评测者的录像丢失不能直接转成产品质量扣分；产品本身缺乏用户可见过程或导出能力，则按细则据证判定。即使缺少过程日志，只要结果与独立验收完整，仍可单列客观结果分。四个人工维度任一缺少合格现场证据，或必需元数据缺失，总分必须为 `null`；不填 0、不填满分，也不只对已有项重新归一化。

空提示词、空输入、无完成条件的空任务不属于有效任务，不能用于证明产品可靠或以零分填满矩阵。只有用例明确研究空输入响应，并在预注册中写明验收条件，才能成为单独的诊断任务。

完整主实验中，各任务等权，每任务内三次重复等权，再对五任务等权平均；五维总分按冻结细则加权至 100 分。不得用运行条数加权把重复较多的任务放大。

指标分别披露：

- 端到端完成率：状态为 `completed` 且独立验收全部通过的槽位数 / 有效实际采集槽位数；平台不支持、已启动的失败与超时保留在分母，`pending` 和 `infra_error` 不进入分母。未完成计划槽位时醒目标记“暂定”，并披露分母与计划数。
- 可执行任务完成率：状态为 `completed` 且独立验收全部通过数 / 实际有效启动数；排除平台不支持，用于描述运行表现，不能代替端到端完成率。
- 条件匹配归因：仅使用条件符合要求的补充实验运行，单独列出排除原因和分母。
- 时间与人工投入：披露每次值、各任务中位数及范围；超时写明“≥ 上限”，不能当作真实完成耗时。
- 总分：所需维度均有合格现场证据时给出运行总分；缺证时总分为 `null`，显示客观结果分及缺失项。只收集了部分任务或重复时，产品均分属于暂定结果，不能作为完整五产品排名。

只有协议已冻结为 `preregistered`、全部 75 个计划槽位取得正式记录、各任务各产品有 3 次有效重复、评分证据齐全且冻结协议一致时，工具才发布完整主实验均分。未齐备时展示逐次记录和分母，不把部分记录均分放进完整比较表。`unsupported` 的操作验证记录仍占对应槽位，但需要四个人工维度的证据才能产生总分。`infra_error` 的槽位须有效重跑后才能满足完整性要求。失败的低分与证据不足的未知分数必须在图表上区别显示。

## 8. 证据、置信依据与复核

每次运行至少保留初始提示词、原始输入版本、可见会话、关键过程片段、原始交付物、独立验收结果和人工操作记录。截图需注明运行 ID、时间与对应步骤；只截一张“已完成”截图不足以支持结果正确或故障恢复的判断。

每条结论使用以下记录格式：

| 字段 | 要求 |
| --- | --- |
| 主张 | 限定到任务、产品、模式、版本和观察行为 |
| 证据位置 | 运行 ID、相对文件路径、消息编号/行号/视频时间戳、独立验收结果 |
| 置信级别 | 人工评分字段用 `high` / `medium` / `low`，说明具体理由；无法判断的项目不赋等级或总分，责任可用 `unresolved` |
| 替代解释 | 模型、Skill、权限、网络、输入适配、操作者或采样波动是否可能解释观察 |
| 复核步骤 | 需要的文件、环境、命令或手工步骤及预期结果 |
| 外推边界 | 结论适用范围；不能把一个任务的现象推成产品普遍能力 |

置信级别用于表达证据支持程度，不是统计置信区间。高置信度的“某次产物错误”可以同时对应无法判定的“错误由 Harness 引起”。具体归因阈值见 [归因规则](attribution.md)。

人工评分必须填写有效现场事件 ID 引用、评分理由、置信依据、替代解释和复核者；责任标签使用 `joint` / `model` / `skill` / `harness` / `environment` / `unresolved`。责任标签只记录有证据支持的判断或候选原因，填写 `harness` 本身不构成因果证明；因果主张仍须通过归因补充对照。

先用独立验收得到客观通过/不通过结果，再对行为项目评分。条件允许时，将交付物去除产品标签后交给第二位复核者独立评分；无法盲评或没有第二位复核者时如实注明。对分歧保留双方原始分数、依据和最终处理，不能静默改分。

只有 3 次重复时，报告各次原始结果、每任务均值或中位数与范围。不得凭小样本宣称显著优于、稳定领先或给出缺少依据的精确概率；若额外计算统计区间，必须标明方法、重采样单位和小样本限制。

## 9. 公开仓库与书面报告

开源仓库应包含冻结方案、版本化用例与输入、评分细则、逐次运行现场、原始交付物、独立验收工具和结果、评分表、结论证据索引及书面报告。公开表格可从运行记录生成，但不能代替原始证据。空模板须醒目标记“待实测”，不能以占位值呈现五产品分数。

在封存前审查待公开材料，移除凭据、个人信息、账户信息与敏感目录，并在元数据中登记脱敏审查状态。保留脱敏清单，说明证据哪些部分被裁切、替换或遮挡；在许可范围内保留足够上下文。登记实际运行元数据，在评分前执行证据封存，防止输入、配置、评分材料或现场文件静默漂移；封存后的更正须另建记录并保留原包，不能静默覆盖或重复封存同一包。`export` 仅生成已审查材料的本地公开副本，不代表已经上传。校验值与封存用于发现文件变化，不能证明文件原本真实，也不能证明执行来自所标注的产品。截图、录像、时间戳和仓库提交记录同样不是单独的真实性保证。

书面报告依次呈现产品与条件登记、方法、证据完整性、逐任务表现、得分与理由、归因补充、限制与复核说明。主实验产品评分表与 Harness 归因判断表分别呈现。所有比较必须能够回到运行证据，未经实际执行的产品只写“待实测”。

每周六的个人周报据已有证据填写本周进展、难点与突破、下周计划。周报不能把计划中的运行写成已完成；邮件草稿和发送行为分开，发送须有用户明确授权。

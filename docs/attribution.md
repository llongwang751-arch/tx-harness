# 模型、Skill 与 Harness 的归因规则

2026-10-24已新增一种可执行路径：[固定响应工具契约对照](../reports/controlled-adapter-v1.md)。用固定程序代替语言模型发出同一工具动作，让真实Codex/DSH执行共同MCP，再核对实际参数和回包。正式四臂通过；该路径不解释Skill内容，隔离的是本次动作生成干扰，不要求猜测隐藏商业模型身份。系统上下文、协议包装及GUI三产品仍未统一；本轮不测真实模型质量、权限沙箱，也不构成五产品纯Harness排名。原真实任务轨道和旧评分单独保留。

本规则用于限制评测结论的责任范围。用户在产品里看到的结果，由模型、Skill、Harness、工具、环境和人工操作共同产生。相同用户提示词只控制了部分输入；如果模型版本、隐藏指令或工具条件未知，就不能由产品分数推导纯 Harness 因果排名。

## 1. 因素定义与责任边界

| 因素 | 本评测定义 | 可观察材料 | 不能默认成立的推断 |
| --- | --- | --- | --- |
| 模型 | 推理、生成、选择动作的模型及版本、采样与上下文条件 | 产品可见模型标识、允许导出的调用元数据、匹配实验配置 | 文本写错就一定是模型的问题；界面同名模型就是同一实际部署 |
| Skill | 可复用领域指令、参考资料、模板、脚本和它们的装载机制 | 用户可见 Skill 文件、版本、启用状态、可授权导出记录 | 上传同一说明文字就等于运行同一原生 Skill；原生 Skill 没显示就代表不存在 |
| Harness | 管理任务、上下文、工具调用、权限、重试、状态、验证与交付的运行组织机制 | 用户可见工具事件、操作顺序、权限交互、恢复行为、产物与匹配实验 | 任何工具失败都由 Harness 引起；具备某个 UI 功能就证明内部机制实现正确 |
| 工具与环境 | 文件系统、执行器、外部服务、网络、额度、操作系统和格式转换 | 服务日志、执行结果、权限设置、输入/输出文件和评测环境记录 | 服务不可用就是产品错误；不同沙箱和工具协议可直接视为相同条件 |
| 操作者 | 导入输入、确认权限、澄清、计时、保存证据和验收的人 | 操作日志、录屏、冻结回复卡、验收命令 | 手工纠错后得到的产物仍代表产品独立完成 |

Skill 的内容与 Skill 的装载/调用机制不同。内容中的错误规则属于 Skill 候选原因；没有装载应装载的规则，可能属于选择或组织机制候选原因，但也可能是模型未选择、权限阻止或入口根本不支持。没有可见证据时保留多种解释。

Harness 的系统指令、上下文整理策略和工具协议经常不可见。它们属于研究边界中的运行机制，但不可见不等于已被控制。界面可选的同名模型，也可能在不同产品中经过不同路由、上下文注入或服务部署。

## 2. 三个层次的结论

### A. 结果事实

例：“在任务 T 的第 2 次运行中，交付文件第 18 行与给定原始资料冲突；独立校验可以复现。”这类结论只描述观察到的产物或操作，不指定责任因素。完整产物和可重复检查可以提供高置信依据。

### B. 行为诊断

例：“发生预设服务错误后，这次运行进行了 3 次可见请求并最终交付；用户无需补充信息。”这描述产品表现出的恢复行为。即使事实可确认，重试是由模型、工具包装层还是 Harness 固定策略触发仍可能未知。

### C. 因果归因

例：“在固定模型、指令、输入、工具与权限的实验中，只禁用了运行器的状态保存后，中断恢复失败；恢复配置后成功。”这一层需要干预、对照和替代解释检查。只比较两个商业产品的最终文件，通常达不到这个证据等级。

报告可以给出高置信的 A 或 B，同时给 C 标记“无法判定”。不能为了形成责任表，把每次失败强行分配给一个因素。

## 3. 最小证据链

沿用户可见的链路定位“最早能够确认的偏离”，并明确不可见部分：

`任务与原始输入 → 可见计划/动作 → 工具请求 → 工具结果 → 状态与后续操作 → 交付物 → 独立验收`

每一个箭头并非所有产品都能提供记录。未提供记录的环节标记未知，不能用助手的叙述补成真实调用。对时间与顺序的描述，需要连续记录或能相互对应的事件 ID；分散截图只能支持截图中可见的内容。

| 观察现象 | 支持的事实 | 候选原因 | 升级归因需要的证据 |
| --- | --- | --- | --- |
| 给定资料与产物中的事实冲突 | 结果错误 | 模型生成、Skill 规则、检索漏项、上下文丢失、输入转换 | 对照原始输入与实际可见读取范围；匹配模型/指令与最小复现；无法看见读取范围时不单归模型 |
| 调用了无关工具或遗漏必要工具 | 可见动作选择不符合任务 | 模型选择、Skill 指导、工具目录、Harness 路由或权限 | 请求与实际执行的对应关系、工具可用性证据；固定模型与工具契约的选择/路由对照 |
| 可见请求正确，工具实际执行参数不同 | 请求与执行不一致 | Harness 参数转换、执行器、日志不完整 | 原始请求、实际执行记录和工具契约一致；最小复现排除工具自身转换 |
| 工具返回成功但没有所需文件 | “成功”返回与产物状态不一致 | 工具虚报、路径解释、沙箱隔离、交付机制 | 返回结果、实际文件位置、可访问性与独立检查；不能仅凭聊天中“成功”断言工具返回成功 |
| 错误后没有重试或备用方案 | 本次没有可见恢复 | 预算不足、权限、模型策略、Skill、Harness 重试机制 | 证明存在允许的可行路径和剩余预算；同故障对照；未知内部策略时只报恢复表现 |
| 恢复会话后忘记约束或重复副作用 | 恢复结果与先前状态不一致 | 模型上下文、状态保存、会话选择、工具幂等性 | 同会话身份、保存记录、恢复边界、工具副作用日志与匹配干预 |
| 自称完成但独立验收不通过 | 完成声明与验收冲突 | 模型判断、验证脚本缺失、Harness 没有强制验收 | 可见验证调用与输出；固定验收工具是否被运行或忽略；无验证记录时不宣称内部完全没验证 |
| 没有日志或不能导出 | 该入口的可复核性限制 | 产品可见接口设计、权限或评测保存问题 | 区分官方接口不存在、账号无权限与评测者未保存；不从缺日志推断内部工具行为 |

“最早可确认的偏离”是定位线索，不自动意味着那个环节是唯一根因。后续交付可能包含多重错误，允许多个候选因素。

## 4. 匹配条件与干预设计

给每一项归因补充建立条件表：

| 条件 | 严格匹配 | 近似或未知时的处理 |
| --- | --- | --- |
| 模型 | 同一可核实版本、部署或可授权调用记录，采样与预算相同 | 同名但实际路由未知只能写近似匹配；不作纯因果结论 |
| Skill | 相同文件版本、启用证据与可见资源 | 默认内置 Skill 未知时不写“无 Skill” |
| 指令与上下文 | 相同任务、同一指令卡、同一输入与可控历史 | 隐藏系统指令差异列为残余混杂因素 |
| 工具 | 相同契约、版本、可用能力、参数与响应条件 | 本地 Python 与远端办公工具不能作为等同工具条件 |
| 权限与环境 | 相同可访问文件、网络、账号额度、时间限制与故障注入 | 产品权限差异可属于产品可用性，不能冒充已隔离的编排差异 |
| 人工操作 | 相同回复规则、次数、时机范围与权限点击政策 | 手工修复或产品特供提示需排除或另报 |

优先采用单个可配置入口内的开关实验，减少跨产品不可见条件差异。可以研究“固定输入与工具，打开/关闭可控的自动重试”或“固定模型与指令，保存/不保存恢复状态”。每次干预只改一个因素，并执行多次配对运行。配对顺序随机化，保留失败与成功。

对商业入口无法操作的内部机制，不把假设写成完成的实验。可以展示“这两次可见行为不同”，并说明需要什么新增证据才能升级为 Harness 因果判断。

## 5. 置信等级

置信等级必须针对具体主张。它不表示产品可信度，也不是一个可以通用换算成百分比的数值。

仓库人工评分字段使用 `high` / `medium` / `low`；“无法判定”不是第四个可赋分置信值。不能依据证据评分时，该项保留空值，总分为 `null`；可以确认评分事实但无法归因时，保留事实置信等级，将责任字段设为 `unresolved`。

| 等级 | 结果/行为主张依据 | 责任归因主张依据 |
| --- | --- | --- |
| 高 | 原始产物与完整可见记录一致；独立检查可复现；重复或交叉证据支持限定范围的结论 | 匹配条件已核实；单因素干预可复现；证据链能定位机制；主要替代解释已经逐项排除 |
| 中 | 原始材料与检查支持结论，但过程片段、单次记录或版本信息有缺口 | 有直接环节证据和部分对照，但残余混杂因素仍可能解释差异；必须写清这些因素 |
| 低 | 只有局部截图、助手自述、非独立验收或容易受适配/操作影响的观察 | 主要依赖现象推测或近似匹配；只能提出候选解释，不能作确定责任判断 |
| 无法判定 | 关键材料缺失、互相冲突或没有验收条件 | 模型/Skill/工具条件关键未知，无法排除多个同样合理解释，或没有机制证据 |

在本项目规模下，重复 3 次可以帮助发现波动，但不能单独提供高置信的广泛因果结论。一个完全可复核的确定性文件错误可以有高事实置信度；三次类似错误也不能自动证明 Harness 是责任方。

## 6. 结论卡与示例

每个得分理由和比较结论都要绑定结论卡：

```text
结论 ID：
主张类型：结果事实 / 行为诊断 / 因果归因
限定范围：产品、版本、模式、任务、重复编号与运行时间
主张：
证据位置：运行 ID、文件、消息编号 / 行号 / 视频时间戳
独立复核：环境、步骤、预期结果
置信等级与具体理由：
模型条件：已知 / 近似 / 未知
Skill 条件：已知 / 近似 / 未知
Harness 证据：
工具、权限、环境与人工因素：
替代解释及已排除依据：
责任结论：model / skill / harness / environment / joint / unresolved
操作者因素：另在原因说明中记录；评测者造成的无效运行不可混为产品责任
外推边界：
```

以下仅是写法示例，不是任何产品的实测结果：

- 可成立：“运行 R 的下载文件缺少规定工作表；用指定脚本检查得到同一结果。结果事实置信高。该入口没有足够工具调用记录，责任无法判定。”
- 需限制：“运行 R 在实际 503 后调用同一服务并交付文件，服务日志与录像对应。恢复行为置信高；重试由哪个内部组件触发未知。”
- 不成立：“产品 P 分数更低，所以它的 Harness 更差。”缺少模型、Skill 与工具条件控制；只能比较登记条件下的产品整体得分。
- 不成立：“没有显示验证日志，所以 Harness 没验证。”缺乏显示不等于不存在；可报告验收未通过及可见验证证据不足。

人工评分中的 `attribution` 标签是结构化记录，评分工具只能检查它是否填齐，不能自动证明其内容真实。标签为 `harness` 且置信为 `high` 时，更不能跳过条件表、干预和替代解释检验，直接写成确定定责。因果证据不够时采用 `unresolved` 或明确的 `joint`，在理由中列出候选因素。

## 7. 公开证据的可信度与范围

只公开用户有权获取的记录和获授权材料。脱敏后对公开文件计算校验值，并说明公开版本与原始记录的差异。校验值支持完整性检查，不证明来源真实性；录屏、时间戳和 Git 提交也不能单独证明未被编辑或标注正确。

提高可复核性的办法是保留完整任务输入、可对应的连续过程、原始产物、独立验收步骤、导出来源和明确的脱敏说明。必要时在合法授权范围内让复核者查看原始记录。缺少这样的条件，主动降低有关来源与归因的置信度。

最终报告并列两张表：一张是登记条件下的端到端任务得分；另一张是具体 Harness 行为主张、证据、匹配程度、置信依据和责任结论。第二张表允许大量“无法判定”，这说明归因边界被遵守，不应通过猜测填满。

## 8. 2026-10-23逐产品落实与选择偏差检查

五款产品实际记录的模型、Skill和边界条件现已逐项核对，见[归因边界表](../reports/attribution-boundaries.md)与[绑定来源的JSON](../reports/attribution-boundaries.json)。这是旧公共材料的事后源审计，不追认为新实验预注册，也不增加产品运行数。原S01配置、之后窗口v2的配置和旧业务题版本分别记录。

模型已经形成某种请求之后的传递检查，只能描述进入该边界的运行。请求能否形成也可能受Harness影响；若只选择正确请求，再用其通过率代表总体Harness能力，会产生选择偏差。必须同时呈现全部尝试、eligible、未进入条件、unknown、上游偏离及环境有效性证据，不比较经过不同筛选的条件通过率。

`eligible=null`不代表已知不适用，更不是产品失败。字节相同也不证明Skill未参与：本批DSH关闭用户/项目发现，但保留内置Office和诊断Skill，第二、三轮存在真实调用元数据。Codex部分发现和扩展开关的记录也不等于完整内置/后台Skill禁用证明。

下一轮只在正式接口和生效记录足以改变某个具体判断时登记：实际模型部署与参数、完整Skill范围、工具/上下文/环境匹配及单一干预缺一项，就保留相应归因限制。仅用同一模型标签、同一提示词或增加重复次数不能补齐控制。当前源核对已完成，未发现可从现有材料直接升级为五产品纯Harness因果排名的依据，本批停止这一更强主张。

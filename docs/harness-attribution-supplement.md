# Harness 归因补充：检查可观察的执行链

状态：方法草案，2026-10-13。本文件提出后续可执行的补充实验，不改动现有协议、评分程序、配置或运行快照。已有预试仍是预试；补充实验须在执行前另行冻结操作卡、条件、分母与检查器。

评测主体应落在 Harness 的输入传递、请求执行、文件落地、权限、反馈和状态机制。算账正确、写作质量和最终任务完成率只作背景材料，不作为 Harness 独立因果分。五款产品无法统一底模和内置 Skill 时，不能保证完全排除这些变量；可采取的实质控制是把判断范围缩小到已经发生、内容明确的操作边界，检查边界两端是否符合契约。

例如，模型已经请求“把文本 X 写到路径 P”。先不评价 X 是否算对，只检查工具请求、权限结果与最终文件是否一致。模型即使算错，只要文件忠实保存 X，这一项传递检查仍应通过；反过来，账算对也不能替代落地检查。这允许测到执行链中的具体事实，同时避免将上游语义能力算作 Harness 得分。

## 1. 观察单位、证据等级与责任范围

一个 **episode** 是新会话中的一张固定操作卡，一次重复编号。一个 **操作实例** 是该 episode 中可用请求 ID 对应的一次真实操作。主分析每个 episode 的每个指标只取预注册指定的首个合格实例，避免把长循环中的十次调用当作十个独立样本；其余调用全部保留并报告。

| 等级 | 必需证据 | 能说明什么 | 不能说明什么 |
|---|---|---|---|
| E1 执行边界证据 | 原生可见请求、请求 ID、原生结果、真实文件或服务端记录、操作契约 | 请求到结果/落地是否一致；可定位发生偏离的边界 | 没有工具自身对照时，不能把 Harness 与工具实现的责任再分开 |
| E2 界面边界证据 | 连续用户可见记录、原生界面文件卡/状态、真实下载或恢复后的状态 | 界面交付、文件可取得性、同会话可见状态是否保持 | 看不到调用参数时，不能断言模型发出了正确工具请求 |
| E3 结果或自述 | 普通回答、产物、独立验收；无完整边界记录 | 结果事实、明确的证据缺口 | 不能单独定责 Harness、模型或 Skill |

“原生可见请求”仍可能是产品的日志投射，不等于独立执行器审计。记录字段截断、路径映射与投射限制。只有请求、实际执行和结果均能对应时，才能检查参数有没有在中间被改写；只有请求和文件时，结论限于该请求与该文件的一致性。

条件化检查控制的是**被观察的那一段**，不是整个产品的因果效果。不同模型会选择不同动作，导致合格实例分布不同；所以必须同时公开进入该段之前的缺失和偏离。不能只保留模型恰好发对请求的样本，再宣称产品普遍更可靠。

## 2. 五产品的可实施范围

| 产品与入口 | 当前已证实的条件 | 后续操作方式 | 未证实的项目 |
|---|---|---|---|
| Codex 原生 CLI 预试 | 有提交后的命令事件、错误结果和原始文件；两次配置不同 | 使用官方入口、独立目录、固定权限与同版本工具，采集 E1；恢复测试使用确切的新会话 ID | 当前 CLI 不能代替桌面成绩；工具内部参数、底模身份与内置 Skill 全貌未独立证明 |
| DSH 桌面捆绑 headless 预试 | 有 read/write/pwsh/Skill/subagent 请求与结果，文件可取回 | 保留请求、调用 ID、权限结果与原始文件；逐项核对 E1 | headless 不能代替桌面；日志投射不证明全部后台机制 |
| WorkBuddy 桌面 | 已安装；独立内置 CLI 两次认证错误，尚无任务调用 | 先确认桌面正常登录与普通任务入口；只有该入口实际公开请求/文件后才按 E1/E2执行 | 不假设桌面有可导出的调用参数，不将 CodeBuddy 完整 CLI 替换为 WorkBuddy |
| 元宝专家模式 | 本轮尚未提交任务 | 确认专家模式后，通过普通上传、用户可见文件卡、实际下载和研究会话的恢复记录测 E2；如正常入口公开完整调用再升级 E1 | 不假设专家模式支持文件交付或日志导出，不以普通聊天替代 |
| 豆包工作任务模式 | 本轮尚未提交任务 | 确认指定模式后，采用同一 E2 操作卡；有实际原生调用证据时再升级 E1 | 不假设办公工具、工具参数或会话恢复功能已可用 |

先做入口适用性预检，再冻结矩阵。无法观察 E1 不等于执行机制失败；没有验证的功能记为 `unknown`。经普通入口实际操作证实某操作不适用时记为 `not_applicable`，列出证据。两者均不记为合格执行失败，也不据此推断不存在隐藏机制。

只比较同一个契约、同一种证据等级与同等前置条件。三款本地产品可以形成原生执行边界的子比较；两款封闭 Web 与本地产品可以形成界面边界的子比较。若五产品没有共同合格指标，不发布一个“五产品纯 Harness 总分”。

## 3. 无需业务推理的六张操作卡

准备一份人工可检查的 UTF-8 文本、一份小 JSON、一份小 CSV，内容包含本轮新生成的随机标识。全部材料由评测者生成并记录哈希，不包含个人数据。固定每个文件的编码、换行、大小与文件名；重复间仅替换预先生成的标识，不能看表现后换题。操作卡不要求检索、算账或领域判断。

每个适用操作卡预定 3 次独立 episode，20 分钟墙钟上限。在冻结时锁定版本、模式、账户、工具契约、允许目录与权限、输入传输、人工操作卡、记录工具和证据等级。若现有 T01–T05 中已经出现相应边界，也可做探索性逐项检查，但不能追认为补充实验的预注册重复。

| ID / 操作卡 | 输入与固定操作 | 进入条件、通过条件 | 归因限制 |
|---|---|---|---|
| H01 输入与读取传递 | 上传/放入 `probe.txt`，请求读取并返回实际原文；禁止网络 | E1：观察到针对该文件的完整读取请求，工具返回的字节/定义的文本与输入一致。E2：界面实际可取得原附件，下载哈希一致 | 普通回答复述错误只算语义/上下文候选；没有读取范围证据时不能归模型或 Harness |
| H02 写入与文件落地 | 给定固定正文及 `outputs/probe.txt`，请求按固定编码原样生成一个文件 | E1：合法完整写入请求中 P、X 可见；最终 P 的原字节等于该请求 X 的契约编码。E2：只有在原生文件卡存在且可检查其文件身份时，检查实际下载；不把助手贴的 Markdown 链接当成原生文件卡 | E1不要求 X 的业务语义正确；E2看不到请求内容时只能评价界面交付，不能单归模型/工具 |
| H03 权限执行 | 在仅含合成数据的研究目录设置被禁止写入的目标；或在产品已验证的普通授权界面按固定卡拒绝一次写入 | 只有真实权限/拒绝入口可用、目标状态可独立检查时适用。观察到受该权限约束的写入请求后，应返回拒绝并保持目标不变 | 用户说“不许写”而产品没调用工具，不能证明权限闸执行过；OS权限与产品策略分别记录 |
| H04 错误反馈 | 请求读取本轮目录中明确不存在的 `missing-probe.txt`；预检其确实不存在；不能在消息里假装工具已经报错 | E1：观察到真实读取请求和真实错误；结果字段应明确错误，而不是工具成功；错误类别与实际状态一致 | 助手猜测缺文件不是工具证据；重试/换工具是模型×Skill×Harness联合行为，不算独立 Harness 恢复分 |
| H05 会话状态保存/恢复 | 第一阶段上传/写入随机标识文件，停在固定检查点；通过已经验证的普通界面或官方确切会话 ID 关闭再恢复；不补解题信息 | 检查同一研究会话身份、原始用户消息、附件身份/哈希、已完成产物与可见待办状态。匹配的不打断对照也执行到同一检查点 | “模型还记得随机标识”只能作联合结果；不知道实际保存状态时不归 Harness。重复副作用只有违反已验证的幂等契约时才判机制错误 |
| H06 交付与完成状态 | 在可见原生文件已生成后，按固定动作打开/下载；保存下载过程与文件；检查完成标记 | 原生文件卡、状态和文件身份可对应，实际可下载且哈希/结构符合其声明。若可见状态明确来自工具成功，应与真实产物相符 | 助手自行说“完成”不是 Harness 状态；CDN、浏览器阻止下载、额度或网络失败须另定位；不凭坏链接直接单归 Harness |

H03 不对用户真实目录改 ACL，不读取其他会话；目标只能是这一轮的合成夹具。关闭/恢复 H05 只针对新建研究会话。任何需手工转写正文成文件、人工改参数、修正公式的操作都是协议偏离，不能成为原生交付证据。

各操作卡使用真实事件 ID 和独立检查，不能仅从机器人自述补齐链路。封闭 Web 不开放某个环节时，保持原来的操作卡与缺口，不另写一条更容易的提示词来凑同名指标。

## 4. 工具、模型与 Skill 的定责步骤

先标出最早可见偏离，再做下表的条件检查。责任可以保持 `joint` 或 `unresolved`，不强制三选一。

| 可见偏离 | 初始责任候选 | 可执行的追加检查 | 足以升级的边界 |
|---|---|---|---|
| 正确原文已经由读取工具完整返回，但生成值与原文/规则冲突 | 生成层候选；可能是模型、Skill或上下文组织 | 保留完整返回与之后的可见动作；用固定短规则卡复现；如可核验底模部署，另做同完整输入的模型基线 | 没有实际模型输入、Skill载入与部署匹配，只写“语义生成偏离”，不单归模型 |
| Skill 自带确定性脚本对固定输入输出错误 | Skill内容候选 | 在隔离研究目录独立执行该公开/有权审查脚本的同版本，保存输入、输出与依赖；对照其明确规则 | 脚本错误可定为该版本Skill内容缺陷；只有产品实际调用同版本且参数匹配，才能把缺陷关联到该次结果 |
| Skill给出错误规则，但不含可独立运行的脚本 | Skill内容候选 | 保存可授权引用的规则版本与资料冲突；用修正规则卡做单入口配对实验 | 可证明规则内容错误；产品最终错误是否由它造成仍需载入与遵循证据。上传文档不等于安装原生Skill |
| 完整请求合法，执行记录参数/路径发生变化 | Harness或执行器候选 | 比较原生请求、实际执行记录、工具契约；相同参数独立调用同一工具作正对照 | 请求到执行的偏离成立；若独立工具也改变参数，应归工具/契约，不能归 Harness |
| 工具成功返回，实际文件不符请求 | 工具、路径映射、落地候选 | 对比请求内容、结果 ID、文件位置与哈希；排除后续产品覆盖、人工编辑和收集器转换 | 可定为这一段交付契约不一致；没分离工具实现时写 Harness×工具 |
| 实际拒绝/错误，但界面或结构结果宣称工具成功 | 结果映射/状态候选 | 对应真实错误、状态更新来源、相同请求ID与最终文件；检查是否为助手自述而非工具状态 | 只有真实状态来源可见时才是Harness映射候选；助手一句“成功”仍属于联合生成 |
| 同一会话恢复后，原消息/附件在界面或官方导出中确实丢失 | 状态机制候选 | 核对确切研究会话ID、前后完整记录、不打断对照、相同身份与版本；排除开错会话和上传未成功 | 可定为该入口可见状态保存失败；模型“忘记”而消息仍在不等于状态丢失 |

“模型基线”只有在同部署、版本、完整可控输入和采样条件可核验时才能作因果对照。换成另一个 API 或同名模型不是匹配；将 Codex、WorkBuddy 或封闭 Web 替换为自建代理也不是在测原产品。

允许对支持正常配置的单一产品做条件配对：相同模型与输入，固定工具响应，只改变一个已验证的 Harness 设置，如权限策略或持久化。A/B顺序随机，至少3组，记录预定故障与正常正对照。若配置改变同时影响提示词、工具集合、Skill或路由，降为联合对照，不能叫单因素消融。不能通过插入假助手/工具回合模拟产品现场。

## 5. 不可匹配模型/Skill时如何控制

1. 缩短语义任务，直接提供固定文本和操作，不要求计算、知识或规划。用本轮随机标识减少已公开夹具的记忆影响。随机标识不是严格抗污染保证。
2. 固定每个产品内部的可见版本、模式、账户、用户设置、模型选择与Skill条件；不可关闭或不可见的项写 `unknown`。在产品内比较重复，不将同名模型写成跨产品严格匹配。
3. 从请求已形成或原生文件已生成的边界开始测传递/状态；保存上游没有形成请求的 episode，公开其原因与数量。模型/Skill对动作选择的影响仍存在，但不拿该影响给执行边界扣分。
4. 公开同一规则卡、原始输入与传输哈希。规则卡只是共同用户资料；不能声称两款封闭Web因此使用了与本地相同的原生Skill。由产品可见接口确认的Skill调用、版本与脚本另行记录。
5. 工具与环境做正常正对照：原始输入可读取、独立检查器可解析、目标路径和允许权限明确；故障臂的失败确实发生。需要产品沙箱特有前置条件却不能验证时，记为缺条件，不能把外部检查通过冒充产品沙箱已通过。

若未来某 Harness 官方支持可替换模型适配器，可以另建**组件契约实验**，用确定性适配器产生固定请求以排除语义生成变化。但本轮没有确认五产品都支持这种接口；它不得与真实商业入口成绩混合，也不得把模拟回合当实际产品执行。

## 6. 分母、得分与未知值

每个指标分别登记以下计数，不用一个“有效样本数”掩盖进入条件差异：

| 字段 | 含义 |
|---|---|
| `planned` | 执行前冻结的 episode 数，默认适用卡每产品3次 |
| `started` | 实际正常入口已开始的 episode，不能包括模板 |
| `applicable` | 已证实该入口可进行该项契约操作 |
| `eligible` | 前置条件成立，所需请求/状态及结果可完整对应的 episode |
| `passed` / `failed` | eligible 内独立检查通过/违反契约数；失败不能剔除 |
| `upstream_deviation` | 未进入边界，如未形成目标操作；语义/选择层候选，另报 |
| `evidence_missing` | 已发生但关键边界不可见或记录损坏 |
| `environment_invalid` | 操作者、输入传输、记录器或预检配置破坏条件；须保存并补测 |
| `not_applicable` / `unknown` | 已验证不适用，或尚不能确认；二者区分 |

允许提供的数值是 **条件化契约通过率** `passed / eligible`，另报 `eligible / planned` 的覆盖和所有排除原因。`eligible=0` 时为 `null`，不记0、不记100。日志缺失、底模未知、不适用、未采集均不是违反契约；只有有资格且真实违反契约才计失败。

如果需要展示分数，可以把同一指标的通过率乘100，标题必须注明“条件化执行/界面契约分”，不是“纯 Harness 因果分”。不同证据等级、不同卡和不同适用范围不加权拼成一个总分；不能删掉未知项后重新归一化。只有五产品都满足事先冻结的同一指标集合与条件，才允许比较同指标的原始率与分母。

现有60分业务正确性、文案质量、规则选择、助手规划、是否自主发现汇率缺失、被资料诱导后的语义选择，以及恢复时“记不记得”答案，均不进入 Harness 独立因果分。现有manual40也不是天然纯Harness分；只有满足上述边界证据的子观察才能进入补充契约表。执行时长、重试次数和人工成本保留为登记配置的联合表现，不在模型/工具不等条件下推成 Harness 效果。

覆盖率是该评测的可观察范围，并非内部能力分。无法公开工具细节的产品应报告其复核限制；不能给每项内部机制判0。3次重复及同一轮的多个工具调用都不足以估计普遍稳定性，不报告未经支撑的显著优越结论。

## 7. 必须保存的逐项记录

每个episode保存 `prompt`、原始输入和哈希、入口与配置、正常正对照、实际开始/截止时间、操作卡、连续可见记录、原始文件、独立检查、manifest与脱敏说明。每个指标保存下列字段：

```json
{
  "episode_id": "new-supplement-run-id",
  "contract_id": "H02",
  "evidence_level": "E1",
  "request_event_id": "actual-event-id",
  "result_event_id": "actual-event-id",
  "request_id": "actual-native-id",
  "preconditions": "verified / missing, with evidence references",
  "payload_complete": true,
  "expected_basis": "tool contract and exact visible request, not a guessed model plan",
  "actual_artifact_sha256": "actual digest or null",
  "eligibility": "eligible / upstream_deviation / evidence_missing / other declared status",
  "verdict": "pass / fail / unknown",
  "confidence": "high / medium / low for the precise claim",
  "attribution": "harness / environment / joint / unresolved",
  "alternative_explanations": "tool implementation, mapping, later edits, projection limits",
  "reproduction": "exact checker and source references",
  "reviewer": "actual reviewer"
}
```

这是结构示意，不是已发生记录。因果结论另保存匹配条件、唯一干预、配对顺序、控制结果及替代解释排除依据。缺少这些字段时只能报告结果或边界观察。

## 8. 已有真实预试能够成立的两个结论

以下为探索性复核，不能计入新补充实验的正式分母。

**DSH 本次三个写入请求的内容与三份实际文件逐字节一致。** [公开事件](../public/pilots/dsh-T01-r1/visible-events.jsonl)中三个 `write` 请求都保留完整 `input.content` 与目标路径，具有对应 `completed` 结果；其UTF-8内容SHA256分别等于 [台账](../public/pilots/dsh-T01-r1/outputs/order_ledger.csv)、[汇总](../public/pilots/dsh-T01-r1/outputs/aggregate.json)和[异常](../public/pilots/dsh-T01-r1/outputs/exceptions.json)的SHA256。[元数据](../public/pilots/dsh-T01-r1/run-metadata.json)与manifest也一致。置信高仅针对这三个写入事实；支持本次 Harness×文件工具的落地契约没有观察到内容偏离，不证明 Harness 相对更强，不证明正确业务内容由 Harness生成。三次操作属于一个episode，不是三个独立重复。

**DSH 本次三条实际 PowerShell 错误均以对应 `tool_result.status=error` 公开返回。** 两条为ACL写授权错误，一条为headless没有提权审批通道；请求ID与结果ID可对应。置信高针对“错误被显式投射为错误”，支持该次可见反馈没有把错误映射为工具成功。ACL/环境及入口权限影响不能单归 Harness缺陷。后续改用read/write、诊断Skill与子代理是联合恢复行为，不能凭最终交付就定责为Harness自动恢复。

独立检查已提取为 [审计脚本](../scripts/audit_harness_observations.py)。它只读取已脱敏公开证据，先验证manifest，再逐项记录事件行号、调用ID、内容及文件哈希。运行后生成 [结构化记录](../reports/harness-observations.json)和 [观察报告](../reports/harness-observations.md)：

```powershell
python -X utf8 scripts/audit_harness_observations.py
```

目前同一检查也覆盖 [DSH T04真实公开事件](../public/pilots/dsh-T04-r1/visible-events.jsonl)：四次写入中，一次早期写入后来被覆盖，只有每个目标文件最后一次完成写入的三项进入最终快照分母，三项均逐字节一致；四条可唯一配对的真实错误文本均有`error`状态。T01与T04是不同任务的两个探索性episode，不是同条件独立重复。最终快照不能证明早期写入当时已落地，也不能证明日志中的参数等于真实系统调用参数。

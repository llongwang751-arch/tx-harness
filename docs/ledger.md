# 运行台账与归因定责规范（第三周）

本页规定本周新增的记账方式：一次运行怎么记、记到哪本账、什么条件下才能进正式比较表、未知怎么处理、结论怎么写、判卷器改动怎么留档。所有数字都由脚本从冻结文件重算，页面本身不产生新结论。

复核入口：

```powershell
python -X utf8 scripts/ledger.py --check          # 只读审计：重算台账、门槛、结论哈希
python -X utf8 scripts/ledger.py reproduce CL-01  # 重跑结论一的可复现实验
python -X utf8 scripts/ledger.py reproduce CL-02  # 重跑结论二的可复现实验
python -X utf8 scripts/independent_check.py       # 独立重写三道判卷守卫
```

## 一、运行记录：十个字段，缺一不可

每条运行写在 `ledger/runs.jsonl`，由 `scripts/ledger_sources.py` 从冻结来源派生；生成文件被手工改动时，`--check` 会因为字节不一致直接报错。

| 字段 | 内容 | 未知时怎么写 |
|---|---|---|
| `run_id` | 唯一编号，全表不可重复 | 不允许缺失 |
| `task` | `case_id` + 题面哈希 + 题目哈希（版本用内容哈希，不用可变标签） | 不允许缺失 |
| `product` | 产品、版本、可执行文件哈希、界面形态 | `version=null` 且必须写 `version_reason` |
| `model` | 后端模型标签、是否经证实、证据来源 | 只有界面标签时写 `attested=false` 并给出原因 |
| `tools` | 工具清单或脚本化工具 | `state=unknown` 时必须写原因 |
| `permissions` | 许可标签与来源指针 | `label=null` 且写原因 |
| `skill_state` | Skill 条件与来源指针 | `label=null` 且写原因 |
| `timing` | 起止时间与时长 | 缺失时写 `reason` |
| `evidence` | 等级、类别、文件哈希、产物哈希、污染状态与依据 | 等级 `none` 表示没有留存证据 |
| `verdict` | 通过/失败/未知/无效、理由、产物分 | 未知与无效必须 `score_for_aggregate=null` |

证据等级按同一套规则判定（`scripts/ledger_sources.py: GRADE_RULE`）：原生事件 + 产物哈希 + 独立重算为 `high`；产物哈希 + 核验记录为 `medium`；只有叙述或截图为 `low`。等级只描述证据，不换成分数。

## 二、六本账，互不相加

`ledger/accounts.json` 把工作量拆成六本账。任何"本周一共做了 N 件事"的写法都违规，因为六本账的口径不同：

| 账 | 含义 | 本次 |
|---|---|---|
| `product_run` | 真正提交给产品的任务/会话 | 47（25 五题端到端、4 固定响应主臂、6 接入校准、4 原生桌面、8 同题重复） |
| `self_test` | 离线回归套件 | 记录在 `ledger/self-test.json`，由 `python -X utf8 scripts/ledger.py selftest` 重新生成 |
| `offline_recompute` | 重算已发布字节 | 4 项，各自有 JSON 指针可回读 |
| `grader_regression` | 合成答案测判卷 | 22 例、20 次开关、旧版误接受 4、v3 误接受/误拒绝 0 |
| `bare_model_probe` | 裸模型探针 | **0**，见下方空账说明 |
| `interface_preflight` | 读配置界面与端点是接口预检 | 3 款产品，计 0 次任务 |

裸模型探针为空是明确结论而不是遗漏：五款产品都没有可证实、又可脱离各自 Harness 调用的同一模型端点，无法与任何产品运行配对；不能配对时，探针结果不改变任何五产品的结论，因此本周不登记。重开条件写在账里：只有当某款产品的确切模型既能披露、又能在 Harness 之外调用时才重开。

## 三、正式比较表的两级门槛

`ledger/formal-table.json` 由台账生成，`reports/week3/formal-table.md` 是同一份数据的人读版本。

- **入选门槛（四道）**：规则冻结（题面与答案哈希等于评测账引用的冻结来源）、题面有效（提交题面以冻结题面开头，桌面产品的 CRLF 行尾按规范化后比较并写明）、证据有效（证据文件与分级规则一致）、无污染（输入副本与冻结输入逐字节一致、产物字节等于被判分字节）。
- **排名门槛（更严）**：入选 + 后端模型经证实 + 协议预注册冻结。

本次结果：47 条产品运行中，29 条正式轨道记录全部通过四道门槛，0 条被剔除；五款产品各有 5 条可判运行；但没有任何一条满足排名门槛（模型均未证实，协议状态为 `draft_before_pilot`），所以正式表给分不给名次，`ranking=null` 并列出原因。

门槛会拒绝，这一点有测试证明：`tests/test_ledger.py` 分别植入"改一个输出字节""换掉题面""制造污染状态""给未知裁定塞分数""复制运行号"，对应检查各自报错。

## 四、未知的三种处理

1. **不记失败、不记零分**：未知裁定不进分子也不进分母，`score_for_aggregate` 保持 `null`。
2. **不按已评部分折算满分**：任何"通过了 3 项所以按比例给分"的写法都不允许；只有完整判分才产生分数。
3. **必须写影响、下一步、停止条件**：`ledger/unknowns.json` 的七项各自带这三段，另有 `scored=false` 与 `denominator=excluded` 两个机器可查的标记。

## 五、判卷器修订：六件套

`ledger/revisions/index.json` 为三道守卫各存一条修订档案，字段固定：

| 件 | 内容 |
|---|---|
| 修前代码 | `harness_eval/core.py` 的归档副本与哈希（旧路径没有该守卫） |
| 修后代码 | `evaluation_v3/grader.py` 与 `supplements/grader-v3/rules.json` 的归档副本与哈希 |
| 正例 | 正确答案在修前修后都通过（G1/G3/G5） |
| 近似错误例 | 只错这一处的答案：修前接受、修后拒绝（N6/N7/N8），字节同时归档 |
| 独立验收 | `scripts/independent_check.py` 不导入判卷代码、不读规则文件，用另一套实现重算 22 例的 36 个守卫判定，与公布结果 0 分歧 |
| 历史复算影响 | 25 份旧产物逐份复算，新增拒绝 0，旧分不重写 |

独立验收第一次并不一致：我按"答案里 `changes` 段的键"推顶层键集，得到只有 `changes` 一个键，与公布的正例冲突。复核发现答案把两个顶层段分开存放（`changes` 与 `unchanged`），正确推导是两段键的并集。修正后 22 例全部一致——这说明独立实现确实独立，而不是抄了规则文件。

## 六、结论：五段结构

`ledger/conclusions/CL-01.json`、`CL-02.json` 统一使用"观察—证据—解释—未排除因素—可复现实验"。每条的 `reproducible_experiment.expected_output_sha256` 是首次冻结的输出哈希，`--check` 会真的重跑该实验并比对；任何输入漂移都会让哈希变化并报错。

结论同时记 `pinned_at` 与 `pinned_against_run_file_sha256`：前者是冻结日期，后者是冻结时 `ledger/runs.jsonl` 的哈希。数据变化必须另记差异并更新这两个字段，不允许只刷新输出哈希——那样会让"结论可复现"退化成"结论跟着数据跑"。

## 七、归因定责：模型、Skill、Harness 怎么分

评测的主体是 Harness，但五款产品的模型与 Skill 都不受我们控制。归因规则只有一条：

> 只有当**模型与 Skill 被固定、仅 Harness 变化**时观察到的差异，才能记作 Harness 的效应；否则只记录"该配置下的端到端表现"。

由此得到三种可记账的情形：

1. **可归因（受控组件轨道）**：模型换成本地脚本，脚本只按请求序号和自己的工具身份动作、从不解析任务或 Skill 文本；工具实现与参数冻结在同一份协议里。此时剩下的变量是产品的传输与编排层。本次四臂覆盖 Codex 与 DSH，可归因范围仅限"单工具成功/错误契约"。
2. **不可归因（五题端到端）**：模型未证实、Skill 状态未证实，分数只能写成"该产品在该配置下的端到端产物表现"。因此正式表给分不给名次。
3. **未知（GUI 三款的内部调用）**：WorkBuddy 的三次校准没有走到共享工具调用，元宝在所查菜单没有共同端点，豆包的自定义连接器只适用于本地电脑。这些是接口边界观察，不是产品能力失败，也不进分数。

每条运行的 `attribution` 字段记录了三件事：`harness_attributable`（布尔或 null）、`controls`（用了哪些对照）、`unexcluded`（还剩哪些没排除的变量）。`harness_attributable=true` 只出现在受控组件轨道的四条主臂上，其余一律 `false`。

## 八、这套东西能证明什么，不能证明什么

- 能证明：每个数字都能从公开字节重算；门槛真的会拒绝；判卷守卫有独立实现复核；结论有可重跑的哈希。
- 不能证明：采集现场的真实性（哈希不能防伪造）、外部人工复核（目前仍是单人 + AI 辅助）、以及任何五款产品之间的因果优劣。
